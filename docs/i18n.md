# Internationalization

Zoviz AI Studio ships translation-ready by default: every user-facing
string, in PHP and in JS, goes through an i18n function.

## PHP

Use core i18n functions with the **literal** text domain
`'zoviz-ai-studio'` — never a constant or a variable, because `wp
i18n make-pot` extracts strings by parsing source text, not by evaluating
PHP:

```php
__( 'Remove Background', 'zoviz-ai-studio' );
esc_html__( 'Zoviz AI Studio', 'zoviz-ai-studio' );
sprintf(
	/* translators: %s: API key label. */
	__( 'Your Zoviz API key "%s" is no longer valid.', 'zoviz-ai-studio' ),
	$key->label()
);
```

Add a `/* translators: ... */` comment above any `sprintf()`/`printf()`
call with placeholders, describing each one in order — translators see
this comment in the `.pot` file.

**Exception:** internal exception messages and log-only strings (developer
diagnostics, never rendered to an end user) are not translated — see
`\InvalidArgumentException` in `ServiceRegistry::register()` for an
example.

## JS

Use `@wordpress/i18n`'s `__()` (and `_n()`, `sprintf()` from the same
package where needed) with the same literal domain:

```js
import { __ } from '@wordpress/i18n';

__( 'Run', 'zoviz-ai-studio' );
```

Every built script bundle's translations are wired up via
`wp_set_script_translations( $handle, 'zoviz-ai-studio', $plugin_dir . 'languages' )`
in `Kernel\Assets::register()` — this reads compiled `.json` translation
files WordPress.org's GlotPress generates per-locale from the `.pot` file;
nothing extra is needed per bundle.

## The `.pot` file

`languages/zoviz-ai-studio.pot` is committed and kept in sync by CI. To
regenerate it locally:

```bash
npx wp-env run cli wp i18n make-pot /var/www/html/wp-content/plugins/zoviz-ai-studio languages/zoviz-ai-studio.pot --domain=zoviz-ai-studio
```

CI's `i18n` job (in `ci.yml`) regenerates it the same way and fails the
build if the committed file drifts from source — so an out-of-date `.pot`
is caught before merge, not at release time.

## What's out of scope

WordPress.org's own translation platform (translate.wordpress.org) handles
actually translating strings into other locales once the plugin is
published — this repository only needs to keep the extractable `.pot`
source strings correct and consistent.
